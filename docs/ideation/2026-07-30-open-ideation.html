Grounding Context

Codebase Context
  • The app already offers a local, loopback-bound web flow, a shared core, and a JSON-capable CLI.
  • Today, the user picks one PDF and one of three broad profiles. Lossy profiles map directly to Ghostscript presets; conservative uses qpdf structural optimization.
  • The core detects no_gain, but the web route still keeps a candidate result for download. Privacy docs also identify stale temporary outputs as an open follow-up.
  • Native tools are a current setup requirement. The product has no account, telemetry, remote storage, editor, OCR, or desktop packaging.
  • External prior art confirms familiar three-strength and batch flows, while local-first tools differentiate through offline processing and reusable automation.

1.

Smart compression planner

Replace the profile-first decision with a locally computed outcome: "email-friendly", "below 10 MB", "upload portal", or "smallest practical file". A preflight identifies likely image-heavy, text-heavy, and already-optimized inputs, proposes a safe path, and tries bounded strategies until it reaches the goal or explains why it cannot.

Basis
direct: the current UI exposes only three fixed profiles, while the core already reports byte-level outcomes. external: Smallpdf positions compression around three strength levels; Ghostscript documents that presets broadly alter input and recommends individual controls for specific quality needs.
Rationale
People usually have a destination constraint, not a preference for a Ghostscript preset. Turning the request into an outcome makes the app easier to trust and creates a natural foundation for document-aware optimization.
Downsides
Requires input analysis, bounded retry policy, and clear limits to avoid unexpectedly long jobs or excessive quality loss.

2.

No-gain protection

When compression yields an equal or larger file, treat that as a completed decision, not as a downloadable "compressed" result. Preserve the original untouched, explain that it is already optimized or unsuitable for the chosen method, and offer one explicit stronger retry rather than silently producing a worse file.

Basis
direct: compressPdf already returns status: "no_gain" and outputSmaller: false, while the web route stores a candidate output anyway.
Rationale
This is a small change with outsized trust value. It makes the product honest at exactly the moment generic compression tools tend to be misleading.
Downsides
Needs a clear retry boundary so the user is not drawn into a confusing loop of increasingly destructive settings.
Confidence
95%
Complexity
Low
3.

Quality confidence loop

For lossy work, locally render representative pages before and after compression, show the pages with the largest visual change, and let the user reject the result. Back this with a small public regression corpus of scan, photo, vector, and text PDFs so profile changes cannot quietly degrade the promise.

Basis
direct: aggressive compression is explicitly allowed to reduce visual fidelity and the plan calls out visual smoke checks. external: Ghostscript warns that presets alter input in multiple ways.
Rationale
Quality is the core trade-off of compression. Making it inspectable turns the local-first promise into a verifiable user benefit instead of a claim.
Downsides
Local page rendering and visual comparison add runtime cost; the product needs to choose representative pages carefully for very large PDFs.
Confidence
82%
Complexity

4.

Batch workspace

Move from a single upload to a local queue for multiple PDFs. Show each file's outcome, let a user rerun only failures with a different goal, use bounded parallelism, and export completed files together without introducing cloud storage.

Basis
direct: batch compression is explicitly deferred in the original product plan. external: PDF24 and Smallpdf position batch workflows as a productivity capability around compression.
Rationale
Batch work is the clearest next user workflow after the single-file experience. It increases usefulness without expanding beyond compression.
Downsides
Requires queue scheduling, disk-space safeguards, cancellation semantics, and a ZIP or folder-save experience that works across browsers.
Confidence
86%
Complexity

5.

Agent batch manifest

Give agents and scripts a first-class batch interface: a JSON Lines manifest, dry-run validation, deterministic output paths, bounded concurrency, and one JSON result per input. It should call the shared core directly, never automate the browser.

Basis
direct: the CLI already has stable single-file JSON output and uses the same core as the web app.
Rationale
This turns an existing contract into an automation surface that agents can reason about safely, while keeping every document local and every result auditable.
Downsides
Public contract design matters: resume behavior, partial failures, output collisions, and JSON schema versioning must be decided deliberately.
Confidence
88%
Complexity
Medium
6.

Local trust receipt and automatic expiry

Show a compact receipt after each job: loopback-only processing, engine and version, output checksum, and whether the temporary workspace has been cleaned. Add automatic expiry for downloaded or abandoned job results, with no document content or metadata retained in the receipt.

Basis
direct: privacy documentation promises local-only processing but notes that stale downloaded results still need automatic expiry. external: local PDF tools compete on the claim that files remain on-device.
Rationale
Privacy is this product's sharpest differentiation. A user-visible, non-invasive receipt makes that promise concrete and audit-friendly.
Downsides
Receipt wording must remain precise so it does not overclaim what the operating system or browser controls.
Confidence
79%
Complexity

7.

Local readiness doctor

Add pdf-compressor doctor and a matching local setup view that checks qpdf and Ghostscript availability, versions, permissions, and a harmless local test job. It should explain how to fix a machine without uploading a sample PDF or leaving the app.

Basis
direct: the repository currently depends on user-installed native tools and reports ENGINE_UNAVAILABLE when they are absent.
Rationale
Local-first software only feels simple when setup failures are self-diagnosing. This reduces support load and makes the web app and CLI more dependable on new machines.
Downsides
Platform-specific installation guidance will need careful maintenance until native binary distribution is decided.
